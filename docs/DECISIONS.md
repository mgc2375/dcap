# Design decisions

These settle the "still to design" table in the v0.1 architecture document. Each one is a starting choice and can be changed.

| Area | Decision | Where |
| --- | --- | --- |
| AI-facing API | None. DCAP adds no tool definition, instruction or command. It listens to what the AI natively says and writes, offers help in one line when it recognises a need, and reads yes or no from the AI's normal reply. On yes, the AI sees exactly the block pasted into its code. `request`, `status`, `results` and `release` are for the operator only. MCP is used only to reach providers, never to reach the AI. | `listener.py`, `api.py` |
| Goal matching | Deterministic matching on normalised words, using Dice overlap with request aliases. A goal runs only if it scores at least 0.75, leads the next goal by at least 0.15, the request has no vague wording, every word and number is covered by that goal's aliases, and the request names at most one target. Anything else exposes tools instead, and goals scoring at least 0.6 come back as suggestions the AI can request by ID. | `resolver.py` |
| Goal registry | Versioned YAML, based on your manifest example. Goals can use cores or child goals. Wiring is type-checked at load, so a bad goal never loads. | `registry.py`, `definitions/goals/` |
| Capability contracts | Named types with one output per core. Inputs and outputs are checked at runtime. AI-facing error codes are `INVALID_INPUT`, `UNAUTHORIZED`, `INVALID_OUTPUT`, `TIMEOUT`, `EXECUTION_FAILED`, `PROVIDER_UNAVAILABLE` and `DEPENDENCY_FAILED`. | `schema.py`, `engine.py` |
| Provider selection | Fixed order: lowest priority number, then provider ID. Unavailable providers are skipped, and a provider whose contract version doesn't match fails at load. A provider marked `simulated: true` loads only with `--simulate` or `DCAP_SIMULATE=1`, and one marked `simulated: false` loads only without it. | `registry.py` |
| Execution engine | Runs stages in dependency levels, in parallel within a level. Each provider gets 1 retry by default, then DCAP fails over to the next. If a stage fails, its dependants are skipped and completed results are returned with status `partial`. | `engine.py` |
| Bridges | YAML templates matched on language, function or method, and sync or async. Without a clearly fitting stub, a predefined block goes in the most recently changed non-test file. Non-Python projects abstain. Automatic selection needs a stub with a relevant name (every word in it must belong to the capability's vocabulary or be one of its verbs), parameters that map by name or alias with no required parameter left over, and a clear winner. Only the last definition of a name is considered. Abstract methods, overloads, Protocol members, special methods and test code are never selected. An operator's bridge must load as one that really delivers the capability. Otherwise DCAP abstains. | `bridges.py`, `definitions/bridges/` |
| Workspace injection | Only empty stubs are edited, inside `# dcap:begin/end` markers. Generated code goes in `dcap_capabilities/`, and only the selected implementation is copied. A native provider with nothing to copy is imported from its installed package when called. A file in a loose folder, or a script in a package, gets the package beside it and an import that works however the file is loaded. Changes are checked first, then applied under a workspace lock with a crash-recoverable journal. A file saved during the check stops the change, and recovery keeps any edit saved after a crash, setting the pre-crash copy aside in `.dcap/recovered/`. Ownership is tracked in `.dcap/manifest.json`. | `workspace.py`, `facade.py` |
| Lifecycle | `release` restores the original file exactly if it hasn't changed since integration. If it has, only the marked region is restored. Hand-edited DCAP files block release unless forced, and are never deleted. If the markers are damaged or the file doesn't parse, nothing is released, even when forced. `status` reports drift and outdated versions, including child goals, core contracts and a changed provider selection. A repeat request reports `conflict` if the code has changed, and updates if the integration is outdated. `update` checks the new version can land before it releases the old one, and keeps the block's file, names and switches. If another integration needs a shared module at the old version, `update` changes nothing and says which to release first. | `workspace.py`, `api.py` |
| Permissions | Named permissions on cores, granted by the operator in `~/.config/dcap/policy.json` (or `$DCAP_POLICY`) and limited by CIDR or host name. A target with a port is checked by its host. The AI-facing interface can't grant them, and a malformed policy grants nothing. The engine checks before any stage runs and again before each stage, because earlier stages can produce new targets. Injected code runs the same checks. The live provider also checks the host of every request it makes, so a link or redirect can't take it outside the grants. | `runtime/policy.py`, `runtime/live.py` |
| Extensibility | Third parties add a directory of the same YAML files, passed with `--definitions`. The operator chooses these, because a provider definition can run code. DCAP never loads them from the workspace automatically. `dcap plug` writes a full set from an MCP server's tool list into the operator's settings, where it loads on its own. `dcap scaffold-provider` drafts a provider for cores that already exist. | `registry.py`, `plug.py` |
| Operator and AI | Operator commands answer a person at a terminal or the holder of the operator key. Anyone else gets no output and exit code 1. An agent's adapter can also refuse a tool call that reaches for the command, the package, the definitions, the policy or DCAP's state. | `operator.py`, `guard.py`, `cli.py` |

## Other choices

- **DCAP raises its hand and waits for a yes.** This replaces the interaction spec's explicit request: the AI's yes is the explicit trigger for injection. The observer still never writes on its own.
- **Listening is deliberately narrow.** It offers on something the AI says it needs, using wording like "I need to", or on a function name or comment in code that clearly matches a goal. Work on the AI's own code, such as fixing or testing, stays silent. Each offer is made once, and a no or two replies that ignore it count as declined for that workspace.
- **The AI only sees what's pasted.** This replaces the interaction spec's status, results and returned-result operations for the AI. Failures go to the operator's log, and the AI gets an empty reply.
- **Nothing runs at the door.** This replaces the spec's Mode B execute-and-return step. A clear goal pastes one switch, off, with the whole chain wired behind it, and the AI turns it on and calls it. `dcap request` still runs goals for the operator.
- **Every clear or vague request integrates.** A request is the explicit trigger, so it writes to the workspace. The observer never writes on its own. Repeating a request changes nothing.
- **Switches are plain environment variables in the AI's code.** A block sets each use case to `"false"`, and generated code reads the variable when called. Turning one on is normal use, so it doesn't count as tampering. An unrelated edit to the block still does. Provider names stay out of the block, so it imports `discover_pages` rather than the name of whichever provider serves it.
- **The paste is modular.** Each core is its own generated module with one `run`, and the block has one import and one switch per core. A file that already binds a name gets `name_2`, so only that line changes, and an update keeps that name. Definitions whose modules or names would collide or can't be written in Python never load.
- **The paste is deterministic.** The same definitions, workspace content and AI sentences give byte-identical offers, blocks and generated files, whatever the hash seed or folder. Definition order doesn't matter either, and capabilities are pasted sorted by core ID. Three inputs can still change the result: the AI's yes or no, which file changed most recently (that's where a block lands), and which providers are installed, since an unavailable one is skipped. Timestamps exist only in `.dcap/`.
- **Text output and paths are declared, not guessed.** A provider sets `text_output: true` if it answers in plain text, and a `before` step lists `paths` for inputs its server needs absolute.
- **Operator runs follow integration.** With `dcap request`, if a goal's integration abstains or conflicts, the goal doesn't run, and the top-level status says so.
- **Results are stored per request for the operator.** The last 100 are kept in `.dcap/results/`.
- **A clear goal doesn't need its parameters at the door,** because generated code takes them when called. `dcap request` still falls back to direct mode when one is missing, because it has to run the goal.
- **"This host" means `127.0.0.1`.** "This site" isn't assumed to mean anything, so it needs an explicit target.
- **Stateful providers declare what runs first.** DCAP opens one MCP session per call, so a provider definition can list `before` tools to run in that session, such as loading a document. An input a `before` tool uses isn't passed to the main tool.
- **Live is the default, and simulated is asked for.** The two never load together. If they did, failover would hand back canned data when a real site was down. The paste is the same in both, because provider names stay out of it.
- **A link belongs to the site it was found on.** A link's `address` is the site being checked, and its `url` is where it points. The engine's scope check is on the site, and the live provider checks each link's own host before requesting it. A link to a host with no grant comes back `skipped`, so one outside link doesn't fail the whole check.
- **Redirects are followed one hop at a time.** Each hop is checked against the grants first. A redirect to a host with no grant is reported as `redirect` with its target, and not requested.
- **`blocked` isn't `broken`.** A link answering 401, 403, 407 or 429 is `blocked`, because the page exists and refused this client. Only `broken` links become issues.
- **A run's grants reach the capability.** The engine passes its grants to a native provider for the length of the call, so `--grant` applies to the provider's own checks. Injected code reads the policy file instead.
- **Contracts grew without a new version.** `url` and `source` were added to pages, links and issues as optional fields, so contract 1 providers that leave them out still pass.
- **The AI can't ask what DCAP has.** It sees a switch only in a paste that follows its own request. A broad request pastes the switches for that one topic, and that paste is still the first time it sees them.
- **A terminal marks the operator.** An agent's shell has no terminal on any stream, so that is the test, with a key for scripts. The key file is found through the account, not `$HOME`, so a caller can't point it elsewhere.
- **A refusal explains nothing.** An operator command run by an agent prints nothing, and a blocked tool call says only "That isn't available here." Help text would list what DCAP can do.
- **The guard fails closed.** If the guard itself faults, the tool call is refused and the fault is logged.
- **Plugged names come from the tool, not a model.** The name is the tool's name, less any vendor word its description never uses, plus words from the description when one word is left. So `nmap_scan` becomes `scan_network`, and the same server always gives the same files.
- **Everything the AI can see is made from the plain name.** The switch, the function and the module path all come from it. The tool's own name is used only to call the server.
- **A plugged tool gets one permission and, where it can, a scope.** A tool that says it only reads gets `<name>.read`, and the rest get `<name>.use`. A required input named like a host, address or URL becomes the scope, and a URL is checked by its host.
- **A plugged server's reply is taken as it comes.** With no declared output, the reply is data if it parses as data, and text otherwise. Built-in and hand-written providers still declare theirs.
- **Provider names stay hidden.** AI-facing responses leave out provider names and raw provider errors. The engine's `debug` trace keeps them for operators.

## Known limits

- **The live provider reads HTML only.** It doesn't run JavaScript, so links a page builds in the browser aren't found. It ignores `robots.txt` rules, apart from reading sitemap locations, because the operator grants the sites it may check.
- **A crawl is capped.** By default it stops at 50 pages, 500 links and 90 seconds, and returns what it has. Links past the cap come back `skipped`.
- **A site is one host and port.** Pages on a subdomain count as external. If the front page redirects to another host, such as `www`, that host needs a grant too and becomes the site.
- **Some servers answer checks differently.** A link is requested with HEAD, then GET if that fails. A server that blocks automated clients shows as `blocked` or `broken` even if the page loads in a browser.
- **Simulated data is canned.** With `--simulate`, `runtime/placeholder.py` returns fixed data and fetches nothing.
- **Python only for bridges.** The observer counts other languages, but DCAP abstains from integrating into them.
- **Native, MCP and HTTP adapters only.** An unknown provider kind counts as unavailable. HTTP secrets come from named environment variables, and redirects are never followed so credentials can't leak to another host.
- **Matching is lexical.** It's deliberately strict, so reworded requests often land in direct mode, with a suggestion when one is close. No semantic matcher is included.
- **Host name scopes aren't resolved.** A grant for a host name matches valid names only, and DCAP doesn't check what it resolves to, so CIDR grants are stricter. A scope only sees strings and objects with an `address` field, so a core with other kinds of scope input needs this extended.
- **Policy isn't a sandbox.** An agent with write access to the policy file can grant itself permissions, so real enforcement needs OS-level separation. The Claude Code hook blocks those writes, but only where the hook is installed.
- **The guard matches known shapes.** It catches the command, the import and the paths written plainly. An agent that builds the name in pieces or copies a file out first can get past it. The terminal check still stops the command line, but not the Python package.
- **Only Claude Code enforces the guard.** The opencode plugin calls `dcap guard` but is untested live, and the Codex driver watches from outside and can't block anything.
- **A workspace-wide search can still reach `.dcap/`.** The guard sees the folder a search starts in, not every file it will read.
- **Plugged names are only as good as the server's.** A tool with a vague name and no description gets a vague name, and `plug` says so under `review`. Use `--rename` for those.
- **Plugged tools that depend on each other aren't chained.** A tool that needs another to run first is flagged, and the `before` step is added by hand.
- **The plug name shows in the import path.** A server plugged in as `nmap` gives `dcap_capabilities.nmap_scan_network`, so name it after the topic.
- **Timeouts are partial for native code.** MCP processes get killed, but a timed-out native call keeps running in its abandoned thread, and injected code doesn't time out native calls at all. The live provider stops itself after its own 90 second budget, inside the 120 seconds its stages are given.
- **Composition is authored.** A request naming two registered goals gets direct mode with both suggested. Only composite goals written in YAML run as one, because DCAP never builds a dependency graph itself.
- **Injected code has no failover.** It checks contracts and retries like the engine, but only the selected implementation is copied, so failing over to another provider needs the engine.
- **Script entry points are found by their contents.** A file in a package is treated as a script only if it has a shebang or a `__main__` guard. Without either, running it directly can't find the package at the import root.
- **Locks need `fcntl`.** Where it doesn't exist, such as on Windows, concurrent DCAP processes aren't kept apart.
- **Package dependencies are only checked.** A provider's `requires` affects availability, and DCAP never installs anything.
- **`update` isn't fully atomic.** It runs as a release and then an integrate. A crash between the two loses the block and its switches.
- **Switches are shared across a process.** Two integrations of the same capability, or a core and a goal with the same name, set the same variable, so a later `"false"` turns off an earlier `"true"`. `status` doesn't report this.
- **A class that grows isn't reported as outdated.** Only an explicit `update` brings in the new capability. A change to a generated runtime file isn't detected either.
- **Crash recovery has gaps.** Recovery only runs when a `Workspace` starts, so a long-lived instance can overwrite another process's unfinished journal. A shared file rewritten after going missing can also read as a hand edit.
- **Listening depends on each agent's adapter.** Only the Codex driver has run with a live agent. It pauses a turn at a message boundary to deliver an offer, and needs session history to resume. The Claude Code hook and the opencode plugin are untested live, and transcript formats may change.
- **An AI can decline what it could write itself.** In a live run, Codex said no to help reading an OpenAPI document and wrote the code. The offer doesn't yet say what the help contains.
- **A live yes is only proven once.** In one live run, Codex said yes and got real output from the pasted code. Its finished tool then called the capability, threw the result away and printed text it had written by hand, because the raw output was hard to read. DCAP can deliver the capability, but can't make the AI use the result.
- **The pasted line beats an outside variable.** Setting a switch to `true` in the shell before running fails, because the block sets it to `"false"` on import. In the live run, Codex tried this first, then set the switch to `"true"` further down its file rather than editing the block.
- **The AI can read the generated code.** `dcap_capabilities/` sits in the workspace, and Codex read every file in it, including the policy check and the provider's command. Nothing hides it yet, so "the AI only sees what's pasted" holds for what DCAP sends, not for what the AI goes looking for.
- **An offer costs a few tokens.** It's about 15 tokens each time DCAP raises its hand, and nothing otherwise.
- **The MCP example is self-contained.** `examples/swagger/` runs its own small read-only OpenAPI reader with Python's standard library, found beside the definition through a `./` path. It reads documents and never calls the API they describe.
- **The Swagger example's permission has no scope.** `api.read` covers any URL once granted, because that example declares none. A plugged server's URL inputs are scoped by host.
